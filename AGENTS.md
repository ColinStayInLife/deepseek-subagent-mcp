# Repository and controller rules

- Execute DeepSeek tasks only when the user explicitly requests `deepseek_subagent` for the current task. Mentioning the tool, reviewing code or editing configuration does not authorize model calls.
- Within an authorized task, the controller may divide bounded independent work, submit background jobs and collect results without asking again for each subtask. Do not extend authorization to unrelated tasks.
- Default DeepSeek Flash effort is `max`; do not lower it unless requested. The controller retains architecture, scientific/model decisions, difficult root causes and final acceptance.
- v1.7 defaults: cumulative input 500000, per-round output 65536 (including reasoning), cumulative output 128000, execution time 1200 seconds. Usually omit these arguments to use project/server defaults; do not copy old 32768/40000 limits into new tasks without a reason. Explicit arguments override project defaults.
- At initial submission, a long task may explicitly use per-round output up to 131072, cumulative output up to 500000 and execution time up to 3600 seconds. Select a matching total output budget. These are ceilings, not output targets; preserve Flash max, inspect effects on incomplete results, and never silently raise a continuation's budget or replay unknown work. Prefer submit/batch for long tasks.
- Prefer `submit` or `batch`, continue useful independent work, and use bounded `wait` only when results are needed. Do not duplicate delegated work or end a task merely because it was submitted.
- Supply an absolute cwd, stable task IDs, clear objectives and acceptance criteria. Keep read-only tasks `allow_write=false`, `allow_shell=false`. Writes and shell require explicit scope and contracts.
- Dependencies on scientific judgment or key interface decisions require controller review before submitting the next task; queue `completed` is not that review.
- Treat `needs_host` as a handoff: claim once, execute an authorized real host tool, then resume using the same task ID and genuine evidence. Do not copy credentials or hidden reasoning. Do not recursively delegate from a subagent.
- Inspect uncertain results before retrying. Cancellation does not roll back existing effects. Retain project-specific resource controls.
- Run offline tests for code changes. Do not call paid models merely to test configuration.
- Never commit API keys, personal paths, user conversation data, runtime state, project-specific data or credentials. Keep examples synthetic and runtime artifacts ignored.
- Within an explicitly authorized task, use `steer` with a stable message_id for corrections to queued/running work. It skips unexecuted obsolete calls at tool boundaries; do not assume a running command stopped or prior effects were undone. Check message application via status.
- After inspecting a safe result, use `followup` with a stable followup_id for bounded rework under the original contract and remaining cumulative budget. `resume` remains host-result handoff only. Changed scientific assumptions/contracts require a separately reviewed task, not permission escalation through feedback.
- Read handoff.json and selected evidence for acceptance. Context pruning preserves pinned original evidence but may omit important middle lines; scientific decisions require checking relevant original data, formulas, units, conditions and sources. No automatic semantic summary or extra summarizer calls are enabled.
- For outcome_unknown, inspect the current job/receipt pins, actual files, command processes and claimed host effects before recording `reconcile`. Confirm all relevant execution stopped. It only releases queue scope and records review; it does not mark scientific work completed, replay effects, or clear command deduplication.
- Implementation assignments should specify the next independently verifiable part and fixed interfaces. Split a complex module across reviewed stages when useful (for example pure receipt validation, then native execution), preserve the scientific model, and avoid compulsory extra planning/reviewer agents or concurrent writes to the same file. Do not accept placeholders or skipped checks as progress that satisfies the task.
- Budget stops now include bounded local verification of configured contract checks, without running generated code, commands or models. Read completion/local_verification and handoff: passed checks do not change the stopped execution status or satisfy dependencies, and not_configured/deferred is not a pass.
- For api_incomplete, inspect diagnostic. reasoning_output_exhausted means the API reported all output tokens as reasoning; the truncated round executed no tools. Prior rounds may still have effects. Reuse inspection_index and actual evidence, then narrow the assignment or take over; never repeat identical paid work, silently increase budgets, or lower Flash max.
